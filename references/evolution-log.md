## Deduplication, Conflict, and Rollback Rules

1. When an identical `source_key`, version, and material scope are fed again, update the access timestamp or return `no-change` rather than creating duplicate method or mechanism entries.
2. When supplementary code, raw data, or an erratum is added for a previously ingested paper, revise the existing card (`revised`), preserve the original interpretation alongside the reason for revision, and link via `supersedes`.
3. When two studies report opposing effects, compare study organisms, response definitions, spatial/temporal scales, treatment intensities, and statistical estimands first. Retain compatible context-dependent conclusions side by side, and tag unresolved discrepancies as `contested`.
4. Passing a computational test upgrades `code_status` only; suitability for a new empirical dataset must still be evaluated from scratch based on experimental design. Journal prestige or impact factor never upgrades evidence origin or code validation status.
5. Execute rollbacks by logging a new evolution event that points back to the restored prior version while preserving the withdrawn entry and the reason for its withdrawal. Never silently erase failed tests, counterexamples, or null findings.
6. As the knowledge base expands, shard individual paper digests into `references/digests/<source_key>.md` while keeping the master index table and direct relative links inside this file so context loading remains lightweight and selective.
